El prototipo funcional implementa los 4 servicios externos en modo simulado con interfaces aisladas en `backend/app/services/`. Se recomienda activarlos en el siguiente orden de prioridad:


| Prioridad     | Servicio                        | Impacto                                                                                                                   | Acción requerida                                                                                                                                                                                                     |
| ------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1 (Alta)**  | **SMTP** (correo real)          | Activa RF-05 (recuperación), RF-06 (verificación), RF-13 (alertas vencimiento) y RF-21 (notificaciones) con envío real | Obtener credenciales SMTP (ej. SendGrid, AWS SES) → configurar`MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM` en `.env` → reemplazar `servicio_correo.py` simulado                                                    |
| **2 (Alta)**  | **Google Maps Distance Matrix** | Activa RF-17 con tiempos reales de llegada como criterio de desempate en emparejamiento                                   | Obtener API Key de Google Cloud con Distance Matrix API habilitada → reemplazar`API_KEY` placeholder en `index.html` y `servicio_mapas.py` → activar cálculo real de `distancia_google_km` y `tiempo_estimado_min` |
| **3 (Media)** | **Gemini IA**                   | Activa RF-18 con normalización semántica real (reconocimiento de entidades + justificación narrativa)                  | Obtener API Key de Google AI Studio → configurar`GEMINI_API_KEY` en `.env` → reemplazar `servicio_ia.py` simulado manteniendo temperatura 0.0 y sin alterar resultado determinista                                  |
| **4 (Media)** | **Google Sheets API v4**        | Activa RF-26 con exportación real a hojas de cálculo compartidas                                                        | Obtener credenciales de servicio Google Cloud (Service Account) → configurar`GOOGLE_SHEETS_CREDENTIALS` en `.env` → reemplazar `servicio_reportes.exportar_sheets()` simulado                                       |

## 9.2 Recomendaciones metodológicas (para futuras investigaciones)

### 9.2.1 Ampliación del alcance funcional


| #  | Recomendación                             | Fundamentación                                                                                                                                                                                                                                            |
| -- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1 | **Integrar predicción de demanda**        | El Capítulo I menciona modelos SARIMA, LSTM y Random Forest como análisis conceptual. Una futura investigación podría implementar predicción de demanda para optimizar proactivamente el acopio de excedentes, reduciendo el desajuste oferta-demanda |
| M2 | **Optimización de rutas de recolección** | Incorporar algoritmos de enrutamiento (VRP — Vehicle Routing Problem) para planificar rutas óptimas de recolección multicliente, reduciendo costos logísticos y huella de carbono                                                                      |
| M3 | **App móvil complementaria**              | Desarrollar una PWA (Progressive Web App) o app nativa para que donantes y receptores puedan registrar lotes, confirmar entregas y recibir notificaciones desde dispositivos móviles en campo                                                             |
| M4 | **Blockchain para trazabilidad fiscal**    | Explorar el uso de blockchain (ej. Hyperledger Fabric) como alternativa al hash SHA-256 encadenado para garantizar inmutabilidad de reportes fiscales con verificación descentralizada ante la DGII                                                       |

### 9.2.2 Mejoras metodológicas del proceso de desarrollo


| #  | Recomendación                           | Fundamentación                                                                                                                                                                                              |
| -- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| M5 | **Pruebas de carga y estrés**           | Ejecutar pruebas con k6 o JMeter para validar RNF-01 (95% GET ≤ 1.5s con 100 usuarios concurrentes), RNF-02 (registro lote ≤ 2s) y RNF-03 (≥ 500,000 lotes sin degradación > 10%)                        |
| M6 | **Estudio de campo con usuarios reales** | Realizar un piloto controlado con al menos 3 bancos de alimentos, 10 donantes y 15 receptores durante ≥ 3 meses para evaluar la efectividad real del sistema en reducción de desperdicio                   |
| M7 | **Métricas de impacto social**          | Definir y medir indicadores de impacto: kg de alimentos rescatados/mes, % de reducción de desperdicio, número de beneficiarios alcanzados, tiempo promedio de entrega, tasa de satisfacción de receptores |
| M8 | **Internacionalización completa**       | Completar el soporte i18n (inglés) para facilitar la transferencia del modelo a otros países del Caribe y Latinoamérica con problemáticas similares de seguridad alimentaria                             |

### 9.2.3 Ampliación del marco normativo


| #   | Recomendación               | Fundamentación                                                                                                                                                                                                                     |

## 9.3 Recomendaciones institucionales (para BARD y organizaciones receptoras)

### 9.3.1 Para el Banco de Alimentos de la República Dominicana (BARD)


| #  | Recomendación                                   | Acción sugerida                                                                                                                                                                                                                                                                            |
| -- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I1 | **Designar un administrador de sistema**         | Nombrar un responsable técnico con acceso al panel administrativo y capacidad de gestionar usuarios, revisar auditorías y generar reportes fiscales. Este rol debe ser ejercido por personal con capacitación en protección de datos (Ley 172-13)                                       |
| I2 | **Protocolo de verificación de receptores**     | Establecer un procedimiento estándar para validar la documentación legal de nuevas organizaciones receptoras (RNC, registro en Procuraduría, personería jurídica vigente) antes de aprobar su registro en el sistema, en cumplimiento de RN-02                                         |
| I3 | **Calibración de parámetros FEFO**             | Revisar y ajustar periódicamente los umbrales de ventana mínima por categoría de perecibilidad (RN-05) según la realidad operativa del banco. Estos valores son parametrizables por el administrador sin modificar código                                                              |
| I4 | **Política de expansión del radio logístico** | El radio piloto está fijado en 35 km (Gran Santo Domingo). Para expansión regional, aumentar el parámetro`radio_max_km` progresivamente evaluando: costo de transporte, tiempo de entrega, y capacidad de cadena de frío                                                                |
| I5 | **Programa de capacitación**                    | Desarrollar un plan de formación para los 4 perfiles de usuario: (a) donantes: cómo registrar lotes y leer alertas FEFO, (b) receptores: cómo confirmar entregas y subir evidencia, (c) banco: gestión de inventario y emparejamiento, (d) administrador: panel de control y auditoría |

### 9.3.2 Para organizaciones receptoras


| #  | Recomendación                                          | Acción sugerida                                                                                                                                                                                                                            |
| -- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I6 | **Mantener actualizada la capacidad de almacenamiento** | Actualizar en el perfil del sistema los cambios en capacidad diaria (kg), infraestructura de cadena de frío y horarios de recepción. Datos desactualizados provocan emparejamientos inviables (RN-07, RN-11)                              |
| I7 | **Confirmar entregas dentro del plazo**                 | Respetar el límite de 48 horas para confirmar/retirar donaciones (RN-12). Los lotes no retirados se liberan automáticamente, perjudicando la eficiencia del sistema y la confianza del donante                                            |
| I8 | **Proporcionar retroalimentación**                     | Utilizar el sistema de calificación (RF-22) para reportar calidad de los alimentos recibidos, puntualidad y estado del empaque. Esta información permite al BARD mejorar la calidad del servicio y detectar donantes con malas prácticas |

### 9.3.3 Gobernanza de datos y cumplimiento continuo


| #   | Recomendación                                   | Acción sugerida                                                                                                                                                                                                                                                             |
| --- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I9  | **Auditoría semestral de protección de datos** | Realizar una revisión interna cada 6 meses del cumplimiento de la Ley 172-13: verificar que todos los usuarios tengan consentimiento registrado, que las solicitudes ARCO se resuelvan en ≤ 15 días hábiles, y que los datos de RNC/cédulas estén cifrados con AES-256 |
| I10 | **Comité de ética de datos**                   | Conformar un comité con representantes del BARD, organizaciones receptoras y un asesor legal para supervisar: (a) no discriminación algorítmica (RN-13), (b) proporcionalidad en la recolección de datos, (c) transparencia en los criterios de emparejamiento           |
| I11 | **Plan de continuidad operativa**                | Documentar y probar anualmente el plan de recuperación ante desastres: restauración de respaldos cifrados (RPO ≤ 24h), tiempo de recuperación del servicio (RTO ≤ 4h), y procedimiento de notificación a usuarios en caso de interrupción prolongada                  |
| I12 | **Convenio con la DGII**                         | Gestionar un acuerdo de colaboración con la Dirección General de Impuestos Internos para validar el formato de los reportes fiscales generados por el sistema (RF-27) y su aceptación como comprobante válido para deducciones del Art. 287 de la Ley 11-92              |
