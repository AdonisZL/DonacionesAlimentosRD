## 7.1 OE1达成情况 — 系统参与者的注册与组织

第一个具体目标是通过结构化表单和集中式数据库注册并组织捐赠者、接收组织和食物银行的信息，以保持对系统参与者的有序、实时和可追溯的控制。该目标通过完整实现注册与认证模块（模块1）得以达成，涵盖十个功能需求（RF-01至RF-08、RF-30和RF-31）。

系统支持三类捐赠者注册——正式化（含RNC和公司名称）、非正式（商户名称和位置）和独立个体（身份证或护照）——以及接收组织（含RNC、检察院登记、存储容量和服务人群）和食物银行（含分支机构、冷藏存储容量和营业时间）。整个注册流程在原子多表事务中执行，同时创建用户、含所需税务数据的法律档案、含PostGIS地理坐标的地址记录，以及符合第172-13号法律的数据处理同意记录。

认证采用签名JSON Web Token和coste为12的bcrypt哈希实现。密码策略要求至少十个字符，包含大写字母、数字和符号（RNF-15）。此外还实现了邮箱账户验证、通过SHA-256不透明令牌找回密码（15分钟过期、一次性使用）、用户自主编辑资料、保留交易历史的逻辑注销（符合第11-92号法律），以及十分钟内五次失败尝试后的临时锁定（RF-30）。前端提供两步注册流程，根据角色显示动态字段，并集成Google Maps Places Autocomplete进行六位小数精度的地理定位。

验证由二十七项100%通过的自动化测试支撑，覆盖bcrypt哈希（5/5）、JWT管理（5/5）、随机令牌生成（4/4）、AES-256加密（6/6）和密码策略（7/7）。验证脚本确认每种角色的成功注册（HTTP 201）、无效RNC的拒绝（HTTP 422）以及所有认证流程的正确运行。因此，OE1被宣布完全达成。

## 7.2 OE2达成情况 — 按剩余保质期索引的动态库存（FEFO）

第二个具体目标是实施动态库存模块，用于存储和控制按剩余保质期索引的剩余食物，以构建减少易腐产品浪费所需的数据结构。该目标通过库存与FEFO管理模块（模块2）实现，涵盖八个功能需求（RF-09至RF-16）。

系统允许登记食品批次，指定产品、食品类别、数量、计量单位、到期日期、生产批号和所需储存条件。每个产品自动归类为四种易腐类别之一——不易腐、半易腐、易腐或冷冻——每类具有可由食物银行管理员参数化配置的最小捐赠窗口期（RN-05）。系统实时计算窗口期 `到期日 − 今天`，并自动拒绝任何窗口期小于等于零的批次（HTTP 422）。库存视图按到期日期升序排列，体现了FAO推荐的FEFO原则。到期警报（≤ 3天）在平台上以琥珀色横幅和脉冲动画显示；邮件发送已实现但处于模拟模式，等待SMTP凭证。模块还包括仅限银行角色的手动库存调整，必须填写原因并生成损耗记录，以及每次操作的不可变日志。

验证由四项100%通过的窗口期计算单元测试支撑（基础案例、过期产品、次日到期和一年到期），以及确认过期批次拒绝、FEFO升序正确、警报检测和历史完整性的验证脚本。OE2被宣布达成，邮件通知（RF-13）处于模拟模式除外。

## 7.3 OE3达成情况 — 供需半自动匹配

第三个具体目标是开发基于确定性规则引擎的供需半自动匹配机制，整合FEFO排序、PostGIS地理空间过滤和接收方约束条件，辅以Gemini API进行论证生成，并要求强制性人工验证。该目标通过智能匹配模块（模块3）实现，涵盖六个功能需求（RF-17至RF-22）。

引擎使用PostGIS地理空间邻近函数（`ST_DWithin`和`ST_Distance`）在可配置半径内搜索兼容接收方（最大75 km，大圣多明各试点35 km），应用接收方容量约束和冷链兼容性（RN-07）。地图服务计算Haversine距离并模拟预计行程时间，架构已为真实Google Maps Distance Matrix做好准备。识别候选方后，AI服务——模拟模式，设计为使用Gemini以temperature 0.0运行且不改变确定性结果——生成自然语言叙事论证。工作流要求强制性人工验证：操作员审查并手动确认每个匹配，之后批次状态变为已预留，设定48小时领取期限（RN-12），并生成自动通知。如果接收方拒绝或未按时领取，批次释放回库存池重新分配。完成的交付支持1至5分评分反馈。

前端集成实时通知铃铛（含未读徽章和下拉菜单）、专用通知页面，以及含批次选择、半径调整、候选方可视化和操作按钮的匹配管理面板。验证由五项100%通过的地图模块测试支撑（SD–Santiago约130 km的Haversine距离、同点零距离、时间模拟），以及确认半径外接收方排除、AI论证存在和所有流程正确运行的验证脚本。OE3被宣布达成，Gemini和Google Maps Distance Matrix已在架构上为真实凭证激活做好准备。

## 7.4 OE4达成情况 — 系统化报表生成

第四个具体目标是通过系统数据的结构化处理生成关于捐赠、库存和分配的系统化报表，以确保透明度并支持税务优惠管理和问责。该目标通过报表模块（模块4）实现，涵盖五个功能需求（RF-23至RF-27）。

系统提供带高级过滤器（日期、捐赠者、类别、状态）和汇总合计的捐赠报表；复用库存服务的FEFO排序当前库存报表；以及已完成分配报表。Google Sheets导出已实现完整CSV生成逻辑，目前处于模拟模式（本地URL），等待Google Cloud凭证。DGII税务模块通过SHA-256链式哈希实现不可变性：每份报表包含前一份的哈希，创建可验证的完整性链；系统支持按版本更正，引用被更正报表的哈希。PDF生成功能正常，数字加密签名待完成以符合DGII第04-2014号规范的全部法律效力。

验证由三项100%通过的自动化测试支撑（空报表结构正确）和确认功能过滤器（6批次、300 kg）、FEFO排序 `[2, 10, 19, 20, 20, 25]`、模拟Sheets导出和税务哈希链（哈希#2正确链接到哈希#1）的验证脚本。OE4的核心功能被宣布达成。

---

## 7.5 OE5达成情况 — 访问控制（RBAC）与数据保护

第五个目标是通过安全认证和角色管理实施访问控制和数据保护机制，以确保捐赠者的机密性和已登记信息的完整性。该目标通过安全与管理模块（模块5）实现，涵盖RF-28、RF-29、RF-32、RNF-12、RNF-15和RN-19。

RBAC访问控制实现了四个层级角色——捐赠者、接收方、食物银行和管理员——使用可重用依赖项限制API端点和前端视图。自注册为管理员被设计阻止。每项关键交易自动记录在审计日志中，捕获身份、操作、时间戳和IP。管理面板实时整合KPI：抢救公斤数、有效率、易腐性分布、按角色用户数和批次状态。税务身份数据使用AES-256-GCM加密保护（6/6测试通过），密码使用bcrypt coste 12处理，并完整实现了符合第172-13号法律的ARCO权利管理（访问、更正、取消、反对），15个工作日最大期限已通过自动化测试验证。

验证由22项100%通过的安全测试和1项ARCO期限计算测试支撑，确认了对管理面板的未授权访问阻止（HTTP 403）、面板指标正确（kg=350，有效率=50%）和审计事件的正确记录。OE5被宣布完全达成。

## 7.6 本章结论

第一章定义的五个具体目标已全部达成。Web系统实现了32项功能需求——覆盖注册与认证、FEFO库存、智能匹配、报表和安全——由27项100%通过的自动化测试支撑。外部服务（SMTP、Gemini AI、Google Sheets和Google Maps Distance Matrix）已在架构上通过模拟接口集成，可在获得真实凭证后立即激活。部分实现的功能（邮件警报、照片证据、Sheets导出和PDF数字签名）不影响功能原型的可操作性，将作为建议在第九章中阐述。

# 第九章. 建议

> **编制日期**：2026-07-31
> **受众**：(a) 系统开发与维护团队，(b) 食品物流与捐赠系统领域的未来研究者，(c) 多米尼加共和国食物银行（BARD）及接收组织。

## 9.1 技术建议

### 9.1.1 激活外部集成

功能原型以隔离接口实现了四个模拟模式的外部服务，便于在不修改架构的情况下替换。建议按运营优先级逐步激活。

第一优先级是真实邮件SMTP服务，因其横跨影响：同时解锁账户验证（RF-06）、密码找回（RF-05）、到期警报（RF-13）和匹配通知（RF-21）。需要从SendGrid或AWS SES等提供商获取SMTP凭证，并在环境文件中配置 `MAIL_USERNAME`、`MAIL_PASSWORD` 和 `MAIL_FROM` 变量。第二优先级是Google Maps Distance Matrix，通过提供真实到达时间完成RF-17；架构已在匹配表中准备了 `distancia_google_km` 和 `tiempo_estimado_min` 字段。第三优先级是Gemini AI，通过实体识别实现真实语义规范化（RF-18），保持temperature 0.0。第四优先级是Google Sheets API v4，实现报表的真实导出（RF-26）。

### 9.1.2 待定功能与生产安全

建议完成三项部分实现的功能。第一，为 `evidencia_entrega` 表（SQL中已存在）创建ORM模型，实现multipart图片上传端点，并在匹配界面添加上传组件以完成RF-25。第二，集成如 `pyHanko` 或 `endesive` 的数字签名库用于税务PDF（RF-27），补充已保证不可变性的SHA-256链式哈希。第三，通过骨架屏加载、表格水平滚动和360像素以下设备的响应式优化改善用户体验。

在安全方面，必须在任何公开发布前激活HTTPS与TLS 1.2+，在预生产环境上执行完整的OWASP ZAP扫描，轮换所有加密密钥（AES-256、JWT secret、API keys）并使用密钥管理服务。建议使用 `pg_dump` 配置每日加密数据库备份，每季度验证完整恢复（RTO ≤ 4h，RPO ≤ 24h），并在认证端点上使用 `slowapi` 实施速率限制。

### 9.1.3 代码质量、测试与无障碍

当前测试覆盖率（综合约55%）需扩大到RNF-16目标：单元测试 ≥ 80%，集成测试 ≥ 60%。建议为所有路由器添加FastAPI `TestClient` 集成测试，并使用Vitest为关键组件创建前端测试。应使用 `react-i18next` 实施国际化，提取文字字面量并准备英文结构（RNF-10）。代码质量应使用SonarQube监控（目标A级），并配置CI/CD流水线，包含 `pytest`、`vitest run`、linting（Ruff/ESLint）、类型检查（Pyright）和安全扫描（`pip-audit`、`npm audit`）。

在无障碍方面，应使用 `axe-core` 对14个页面按WCAG 2.1 AA进行审计（目标 ≥ 90%页面合规）。建议对 ≥ 5位代表性用户进行SUS可用性测试，测量首次捐赠时间（目标 ≤ 5分钟）和SUS评分（目标 ≥ 70）。应删除孤儿文件 `index.css` 和 `App.css`。

## 9.2 面向未来研究的方法论建议

在功能层面，建议集成基于时间序列的需求预测模型——SARIMA、LSTM或Random Forest——其概念分析已在第一章中涉及，以主动优化剩余物资收集。引入VRP（车辆路径问题）路由算法可规划多客户最优收集路线。开发配套PWA将便于从现场移动设备访问。探索区块链技术——如Hyperledger Fabric——可为税务不可变性的去中心化验证提供SHA-256哈希的替代方案。

在方法论层面，必须使用k6或JMeter执行负载测试，以验证性能非功能需求：100并发用户下95%的GET ≤ 1.5秒（RNF-01）、批次登记 ≤ 2秒（RNF-02）和 ≥ 500,000批次无超过10%的性能下降（RNF-03）。建议开展受控实地研究，至少包含3个食物银行、10位捐赠者和15个接收组织，持续 ≥ 3个月，衡量社会影响指标：每月抢救公斤数、浪费减少百分比、受益人数和接收方满意度。

完整的英文国际化将便于模型推广到加勒比和拉丁美洲其他国家。如果系统扩展到欧盟，需实施GDPR的额外要求。对于大规模机构部署，建议准备ISMS文档以获取ISO/IEC 27001认证。

## 9.3 机构建议

### 9.3.1 面向多米尼加共和国食物银行（BARD）

BARD作为协调实体，应指定一名系统管理员，具有控制面板访问权限、用户和权限管理能力，以及审计和税务报表责任，并接受数据保护培训（第172-13号法律）。必须建立新接收组织的文件验证标准程序——验证RNC、检察院登记和有效法人资格——在批准其注册之前（RN-02）。FEFO窗口期阈值（RN-05）应根据运营经验定期校准。物流半径政策应从35 km试点逐步扩展，评估运输成本、交付时间和冷链能力。建议为四种用户画像制定结构化培训计划：捐赠者（批次登记和FEFO警报）、接收方（交付确认和证据上传）、银行（库存和匹配管理）和管理员（控制面板和审计）。

### 9.3.2 面向接收组织

接收组织必须保持其资料信息更新——每日容量、冷链基础设施和接收时间——因为过时数据会导致不可行的匹配（RN-07、RN-11）。必须遵守48小时确认和领取捐赠的期限（RN-12）；未领取的批次将自动释放。建议积极使用反馈系统（RF-22）报告食品质量、准时性和包装状况，这些信息使BARD能够改进服务并发现不良做法。

### 9.3.3 数据治理与持续合规

建议每半年进行一次数据保护审计，验证已记录的同意、ARCO请求在15个工作日内解决以及税务数据的AES-256加密。应组建由BARD代表、接收组织和法律顾问组成的数据伦理委员会，监督算法无歧视（RN-13）、数据收集的比例性和匹配标准的透明度。应每年记录并测试运营连续性计划，要求RPO ≤ 24h、RTO ≤ 4h及用户通知程序。最后，建议与DGII管理正式合作协议，以验证系统生成的税务报表格式及其作为第11-92号法律第287条可抵扣有效凭证的接受度。
